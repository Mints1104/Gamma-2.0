# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Gamma is a native Android app (Kotlin, single `app` module, package `com.mints.projectgammatwo`) that aggregates and displays live Pokémon GO Team Rocket invasion and quest data scraped from a set of community "pokemap" websites, with filtering, favorites (including the current local time at each one), a floating overlay window, and one-tap teleports into spoofing apps (iPogo/Pokemod/custom deeplink, or GPS Joystick).

## Commands

Build/test from the repo root (Gradle wrapper). Use `./gradlew` in Bash/Git Bash, `.\gradlew.bat` in PowerShell.

- Assemble debug APK: `./gradlew assembleDebug`
- Assemble release APK: `./gradlew assembleRelease` (minified + shrunk, uses the debug signing config — see `app/build.gradle.kts`; distributable builds are signed with the release keystore from Android Studio)
- Install debug build to a connected device/emulator: `./gradlew installDebug`
- Run unit tests (JVM, `app/src/test`): `./gradlew test`
- Run a single unit test class: `./gradlew test --tests "com.mints.projectgammatwo.ExampleUnitTest"`
- Run instrumented tests (`app/src/androidTest`, needs a device/emulator): `./gradlew connectedAndroidTest`
- Android Lint: `./gradlew lint`
- Full check (lint + tests): `./gradlew check`

Debug builds use `applicationIdSuffix = ".debug"` and the launcher name "Gamma Debug" (`app/src/debug/res`), so they install alongside the keystore-signed release app instead of requiring it to be uninstalled (which would wipe its data). Use the `.debug` package name with `adb` (e.g. `run-as com.mints.projectgammatwo.debug`).

Note: `app/src/test` and `app/src/androidTest` currently only contain the default template tests generated by Android Studio — there is no real test suite to run or extend as a baseline. Classes that take a `Context` can be unit-tested with a `ContextWrapper(null)` subclass overriding `getSharedPreferences` to return an in-memory `SharedPreferences`.

Release builds strip `Log.d`/`Log.v` via `-assumenosideeffects` in `app/proguard-rules.pro`; `Log.i`/`w`/`e` are kept. Debug builds keep all logging, which is the easiest way to observe fetches on a device.

## Architecture

### Layering

Fragments (`ui/`) + `AndroidViewModel`s (`viewmodels/`) using `LiveData`, wired through the Navigation Component (`res/navigation/nav_graph.xml`) inside a single `MainActivity`. There is no DI framework (no Hilt/Dagger/Koin) — repositories and managers are constructed directly wherever needed, often as light "manager" classes over `SharedPreferences` rather than a database. Room is a declared dependency but is currently unused (no `@Entity`/`@Dao`/`RoomDatabase` anywhere) — all persistence is `SharedPreferences` (sometimes JSON-encoded via Gson) or `kotlinx.serialization` for import/export.

`MainActivity` pops back to the start destination on every bottom-nav tab change, destroying the previous fragment. `HomeViewModel` and `QuestsViewModel` are therefore **activity-scoped** (`activityViewModels()` / `ViewModelProvider(requireActivity())`) so their lists survive tab switches; the quest list and the filter screen share one `QuestsViewModel`. Screens call `refreshIfStale()` on view creation, which refetches only when the published list is older than its window (60s; 5 min for quests) or was built from different inputs — data sources, filters, and `fingerprint()`s of the deleted-invasion and visited-quest stores, so changes made elsewhere (the overlay, a history screen's clear, an import) still trigger a refetch. Only a fetch where every source succeeded is recorded as published. The invasion list is sorted in full and *then* capped at 500 (`applySorting`); capping first made both sort modes reorder an arbitrary API-ordered subset. Pull-to-refresh calls the `fetch*()` methods directly. Anything that changes what a list shows must go through the view model (e.g. `deleteInvasion`, `markVisited`), not just the adapter, or a return to the tab replays the stale list.

One-shot UI events such as error toasts are exposed as `LiveData<Event<T>>` (`helpers/Event`) and read with `consume()`; a plain `LiveData` replays its last value to every new observer, re-showing the toast on each rotation or tab return.

### Multi-source data aggregation

The app pulls from several independently-hosted, per-city map backends (`ApiClient.DATA_SOURCE_URLS`, e.g. `NYC`, `LONDON`, `Singapore`, `VANCOUVER`, `SYDNEY`), each exposing the same PHP endpoints (`pokestop.php`, `quests.php`) via Retrofit (`InvasionApi`, `QuestsApiService`). All requests share one OkHttp client (`ApiClient.httpClient`) and one Retrofit per base URL (`ApiClient.getApiForBaseUrl`/`questsApi`); don't build clients elsewhere. Which sources are active is user-configurable (`DataSourcePreferences`, default `NYC`).

`HomeViewModel.fetchInvasions()` and `QuestsViewModel.fetchQuests()` cancel any fetch still in flight, fan out one coroutine per enabled source with `async {}`, fetch concurrently, then flatten/merge/filter/sort off the main thread (`Dispatchers.Default`/`IO`). When adding a new fetch path, follow the existing pattern: per-source `try/catch` that degrades that source to an empty result on failure rather than failing the whole fetch, and **always catch `CancellationException` before the general `Exception` catch and rethrow it**. Also call `ensureActive()` at the top of `IOException`/`Exception` catches: cancelling an OkHttp call surfaces as `IOException("Canceled")`, not `CancellationException`, and reporting it showed a spurious "Network error" toast on every superseded fetch.

Gson ignores Kotlin default values and leaves absent JSON fields `null` even when the property type is non-null. Any model field that can be missing — from the API, or from an older app version's cached JSON — must be declared nullable (see `Quests.Filters.t8`/`t9`, which crashed the quest filter screen when read from a pre-4.0 cache).

### Persistence concurrency

`DeletedInvasionsRepository` and `VisitedQuestsPreferences` do read-modify-writes on a single `StringSet` and are instantiated in several places and used from several threads. All their read-modify-writes run under a **process-wide** lock (a companion-object `lock`, since a per-instance lock wouldn't cover the other instances), and their pruning getters only write when something actually changed. Keep new write paths inside the lock; without it, concurrent writers silently dropped each other's entries (deleted invasions reappearing, undercounted daily limit).

### Filtering system

`FilterPreferences` is the single source of truth for both "Rocket" (invasion) filters and "Quest" filters, backed by two separate `SharedPreferences` files (`invasion_filters` and `quest_filters`, the latter's name exposed as `FilterPreferences.QUEST_PREF_NAME` so `QuestFilterPreferences` — a thinner accessor over the same file, used by the view models — stays in sync rather than duplicating the string). Each filter type supports: a "live" enabled set, named saved snapshots ("save as new" / "update"), and an "active filter name" that is cleared before any write and re-set after, so that resume-time reconciliation hooks never observe a write in progress.

Quest filters have an extra layer of complexity: many quests share the same reward type+id but differ by amount or condition text (e.g. "Spin 1 stop" vs "Spin 14 stops" both rewarding the same Pokémon encounter). `QuestsViewModel.fetchQuests()` computes these as `SubVariant`s per base filter key (`"type,amount,id"` triples) on every fetch and caches them (24h TTL) so the filter UI has something to render on cold start before the network responds, and `FilterFragment` renders expandable checkbox groups (main checkbox + variant sub-checkboxes) for these by hand — it's a large, stateful, manually-built `LinearLayout` tree (not a `RecyclerView`), with an `isRebuildingQuestFilters` re-entrancy guard to stop checkbox listeners from firing while the tree is being torn down and rebuilt. This area has had several correctness bugs (see commit history: "Fixed bug where unchecking one variant... could prevent filtering other ticked variants", "Revamped filters to support variants"); when touching it, preserve the base-filter-plus-condition-key invariant (`enabledQuestFilters` holds base filter strings like `"4,0,483"`; `enabledEncounterConditions` holds the finer-grained `"type|id|amount|condition|reward"` keys that disambiguate variants) and re-run `reconcileVariantSelections` mentally for any new write path.

Network-derived quest data (the API's filter lists, the sub-variants and their timestamps) lives in its own prefs file via `data/QuestCache`, not in `quest_filters`, so it can be excluded from backups. Pokémon names come from PokeAPI through the process-wide `PokemonRepository.getInstance()`, which caches in memory and in `pokemon_cache` and does disk I/O off the main thread.

### Backups

`res/xml/data_extraction_rules.xml` (Android 12+) and `res/xml/backup_rules.xml` (older) exclude caches and runtime state from cloud backup and device transfer: `quest_cache.xml`, `pokemon_cache.xml`, `overlay_prefs.xml`. Restoring a stale cache onto a newer app version is how the pre-4.0 quest cache crash reached users. Keep both files in sync, and keep regenerable data out of prefs files that also hold user settings.

### Overlay service

`OverlayService` is a foreground `Service` (permission: `SYSTEM_ALERT_WINDOW`, type `specialUse`) that draws a floating, draggable window via `WindowManager` independent of `MainActivity`/its fragments — used so a player can see invasions/quests/favorites while another app (e.g. a spoofer) has focus. It owns a `ViewModelStore` holding its own `HomeViewModel`/`QuestsViewModel` (reused across refreshes, cleared in `onDestroy` so their scopes are cancelled) and a `serviceScope` for its own background work; it does not share the activity's view models. Its favorites and filters panels are separate `WindowManager` windows that are hidden (not removed) when closed, so teardown must remove every attached window (`cleanupOverlays()`, keyed on `isAttachedToWindow`). Its list only refreshes on demand, so ▶/◀ go through `nextLiveInvasionIndex` (`helpers/InvasionNavigation`), which skips invasions with under a minute left and refetches when none remain. Started via `OverlayServiceManager.startOverlayService(mode)`; the overlay permission itself must already be granted (see `dialog_overlay_permission.xml`) — this class does not request it. The invasion and quest screens share one Start/Stop button through `helpers/OverlayButtonController` (constructed as a fragment property, since it registers the Android 13+ `POST_NOTIFICATIONS` request; the overlay starts whatever the answer). Whether the service is alive is `OverlayService.running` (in-memory `LiveData`, so it can't go stale across a crash or force-stop the way a prefs flag did); the notification's Stop action sends `ACTION_STOP`. `CurrentInvasionData`/`CurrentQuestData` are process-wide mutable singletons holding the last-fetched lists, used to hand data between the activity's view models and the overlay service without a shared ViewModel scope.

### Teleports

Every teleport (invasion/quest list items, favorites, overlay buttons) must go through `Teleporter.teleport(context, lat, lng)` (`helpers/Teleporter`). It honours the teleport method setting ("joystick" sends GPS Joystick's teleport intent; otherwise it opens the URL from `DeeplinkManager.generateDeeplink`, which applies the iPogo/Pokemod/custom-template preference), adds `FLAG_ACTIVITY_NEW_TASK` when called outside an Activity, and reports a missing target app with a toast instead of crashing. It returns whether the teleport launched; callers that mark an item handled (delete an invasion, visit a quest, count toward the daily limit) must only do so on success. `generateDeeplink` substitutes `%s` literally (custom templates are URLs and may contain percent-encoding, which `String.format` would choke on) and writes coordinates as plain decimals (`Double.toString` uses scientific notation below 0.001). Copy buttons use the same `toPlainCoordinate()` (`helpers/Coordinates`), not the locale-formatted display text, which gives `40,77839` in comma-decimal locales; `isValidLatLng` there is the range check for user-entered coordinates. The known GPS Joystick packages are listed both in `Teleporter` and in the manifest's `<queries>` block (required for package visibility on Android 11+) — keep them in sync.

### Settings import/export

`ExportData` (kotlinx.serialization `@Serializable`) is the snapshot format for the settings backup/restore feature in `SettingsFragment`. Export writes a JSON file through the system picker (`ActivityResultContracts.CreateDocument`); import reads a file (`OpenDocument`) or pasted JSON. It carries data sources, filters (the live rocket and quest selections, saved filters, and encounter-condition snapshots Base64-encoded via `encodeConditionSet`/`encodeConditionMap`), favorites, home coordinates, overlay customization, and deeplink prefs. Because exported files from older app versions must keep importing, fields are never removed or repurposed when they change format — old fields are kept and commented as legacy/deserialization-only (e.g. `enabledQuests`, `savedQuestSpindaForms`), with encode/decode helpers falling back to the legacy field when the new one is empty. New fields must have defaults (older exports won't have them). Follow this pattern when extending export/import.

Import replaces every setting, so `importSettings` first rejects anything that isn't a JSON object with at least one `ExportData` field (the lenient Gson fallback otherwise reads any text as an all-null backup and wipes everything). A custom teleport link is never applied silently: when an import would change where teleports go, `ConfirmImportedDeeplinkDialogFragment` shows the link and applies it only if accepted. The paste-JSON dialogs (settings and favorites) are `JsonImportDialogFragment`s and the confirmation is a DialogFragment too, so they survive rotation and process death; their results come back through fragment-result listeners registered in the host's `onCreate`, which is the only place a listener exists when a restored dialog reports back.

Importing saved filters goes through the live selection (`saveCurrentAsFilter` snapshots the live set), so the import restores the live rocket and quest selections *after* the saved-filter loops when no named filter is active. Favorites go through `FavoritesManager` in both directions so the manual order (`favorites_order`) is preserved.
