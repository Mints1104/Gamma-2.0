## What this is

Gamma is a native Android app (Kotlin, single `app` module, package `com.mints.projectgammatwo`) that aggregates and displays live Pokémon GO Team Rocket invasion, quest, and raid data scraped from a set of community "pokemap" websites, with filtering, favorites, a floating overlay window, and one-tap teleport deeplinks into spoofing apps (iPogo/Pokemod/custom).

## Commands

Build/test from the repo root (Gradle wrapper). Use `./gradlew` in Bash/Git Bash, `.\gradlew.bat` in PowerShell.

- Assemble debug APK: `./gradlew assembleDebug`
- Assemble release APK: `./gradlew assembleRelease` (minified + shrunk, uses the debug signing config — see `app/build.gradle.kts`)
- Install debug build to a connected device/emulator: `./gradlew installDebug`
- Run unit tests (JVM, `app/src/test`): `./gradlew test`
- Run a single unit test class: `./gradlew test --tests "com.mints.projectgammatwo.ExampleUnitTest"`
- Run instrumented tests (`app/src/androidTest`, needs a device/emulator): `./gradlew connectedAndroidTest`
- Android Lint: `./gradlew lint`
- Full check (lint + tests): `./gradlew check`

Note: `app/src/test` and `app/src/androidTest` currently only contain the default template tests generated by Android Studio — there is no real test suite to run or extend as a baseline.

## Architecture

### Layering

Fragments (`ui/`) + `AndroidViewModel`s (`viewmodels/`) using `LiveData`, wired through the Navigation Component (`res/navigation/nav_graph.xml`) inside a single `MainActivity`. There is no DI framework (no Hilt/Dagger/Koin) — repositories and managers are constructed directly wherever needed, often as light "manager" classes over `SharedPreferences` rather than a database. Room is a declared dependency but is currently unused (no `@Entity`/`@Dao`/`RoomDatabase` anywhere) — all persistence is `SharedPreferences` (sometimes JSON-encoded via Gson) or `kotlinx.serialization` for import/export.

### Multi-source data aggregation

The app pulls from several independently-hosted, per-city map backends (`ApiClient.DATA_SOURCE_URLS`, e.g. `NYC`, `LONDON`, `Singapore`, `VANCOUVER`, `SYDNEY`), each exposing the same PHP endpoints (`pokestop.php`, `quests.php`) via Retrofit (`InvasionApi`, `QuestsApiService`, `RaidApiService`). Which sources are active is user-configurable (`DataSourcePreferences`, default `NYC`). `HomeViewModel.fetchInvasions()` and `QuestsViewModel.fetchQuests()` fan out one coroutine per enabled source with `async {}`, fetch concurrently, then flatten/merge/filter/sort the combined results off the main thread (`Dispatchers.Default`/`IO`). When adding a new fetch path, follow the existing pattern: per-source `try/catch` that degrades that source to an empty list on failure rather than failing the whole fetch, and **always catch `CancellationException` before the general `Exception` catch and rethrow it** — treating cancellation from a superseded fetch (e.g. rapid pull-to-refresh or sort-mode changes) as a user-facing error was a real, previously-fixed bug (see `COROUTINE_CANCELLATION_FIX.md`).

### Filtering system

`FilterPreferences` is the single source of truth for both "Rocket" (invasion) filters and "Quest" filters, backed by two separate `SharedPreferences` files (`invasion_filters` and `quest_filters`, the latter's name exposed as `FilterPreferences.QUEST_PREF_NAME` so `QuestFilterPreferences` — a thinner accessor over the same file, used by the view models — stays in sync rather than duplicating the string). Each filter type supports: a "live" enabled set, named saved snapshots ("save as new" / "update"), and an "active filter name" that is cleared before any write and re-set after, so that resume-time reconciliation hooks never observe a write in progress.

Quest filters have an extra layer of complexity: many quests share the same reward type+id but differ by amount or condition text (e.g. "Spin 1 stop" vs "Spin 14 stops" both rewarding the same Pokémon encounter). `QuestsViewModel.fetchQuests()` computes these as `SubVariant`s per base filter key (`"type,amount,id"` triples) on every fetch, caches them to `SharedPreferences` (`quest_sub_variants`, 24h TTL) so the filter UI has something to render on cold start before the network responds, and `FilterFragment` renders expandable checkbox groups (main checkbox + variant sub-checkboxes) for these by hand — it's a large, stateful, manually-built `LinearLayout` tree (not a `RecyclerView`), with an `isRebuildingQuestFilters` re-entrancy guard to stop checkbox listeners from firing while the tree is being torn down and rebuilt. This area has had several correctness bugs (see commit history: "Fixed bug where unchecking one variant... could prevent filtering other ticked variants", "Revamped filters to support variants"); when touching it, preserve the base-filter-plus-condition-key invariant (`enabledQuestFilters` holds base filter strings like `"4,0,483"`; `enabledEncounterConditions` holds the finer-grained `"type|id|amount|condition|reward"` keys that disambiguate variants) and re-run `reconcileVariantSelections` mentally for any new write path.

### Overlay service

`OverlayService` is a foreground `Service` (permission: `SYSTEM_ALERT_WINDOW`, type `specialUse`) that draws a floating, draggable window via `WindowManager` independent of `MainActivity`/its fragments — used so a player can see invasions/quests/favorites while another app (e.g. a spoofer) has focus. It holds its own `HomeViewModel` instance and observes its `LiveData` directly rather than sharing the activity's view model. Started via `OverlayServiceManager.startOverlayService(mode)`; the overlay permission itself must already be granted (see `dialog_overlay_permission.xml`) — this class does not request it. `CurrentInvasionData`/`CurrentQuestData` are process-wide mutable singletons holding the last-fetched lists, used to hand data between the activity's view models and the overlay service without a shared ViewModel scope.

### Teleport deeplinks

Every "teleport" action (invasion/quest/raid list items, favorites, overlay buttons) must go through `DeeplinkManager.getInstance(context).generateDeeplink(lat, lng)` rather than building a URL inline — it centralizes the iPogo/Pokemod/custom-URL-template preference (`SettingsFragment`) so changing the preference affects every teleport button at once.

### Settings import/export

`ExportData` (kotlinx.serialization `@Serializable`) is the on-disk snapshot format for the settings backup/restore feature in `SettingsFragment`. It carries data sources, filters (including per-filter encounter-condition snapshots, Base64-encoded via `encodeConditionSet`/`encodeConditionMap` for compactness), favorites, home coordinates, overlay customization, and deeplink prefs. Because exported files from older app versions must keep importing, fields are never removed when they change format — old fields are kept and commented as legacy/deserialization-only (e.g. `enabledQuestFilters`, `savedQuestSpindaForms`), with encode/decode helpers falling back to the legacy field when the new one is empty. Follow this pattern (add new fields, don't repurpose or delete old ones) when extending export/import.
